How a language model works

The ideas, in plain English, with no code: what a language model actually is, how text becomes numbers, what “learning” means, and how the pieces fit. This chapter is optional theory — read it first if you like the why before the how, or skip ahead: Part 1 builds every one of these ideas in real, runnable code, and Part 2 fine-tunes a real model into a useful expert.

The whole thing in one breath: a language model is a mathematical function with a great many adjustable numbers — its parameters (you'll also hear them called its weights): the dials of the function — that, given some text so far, predicts what comes next. Training tunes those dials (countless tiny nudges) until coherent language falls out. Generation runs the function in a loop to write.

Everything below unpacks that: how text becomes numbers, how the model “looks back” at what it has read, how it measures its own mistakes, and how it slowly improves.

No Python here. This page is concepts and pictures only. Every idea reappears as real code in Part 1 · Pre-training; each section links across to where it's built.

Part 0 · Concepts

1

What a model actually does

Strip away the mystique and a language model does one narrow thing: given the text so far, it predicts what comes next. Not whole thoughts, just the next small chunk (a token: a word or word-piece). To write a sentence it just does this over and over, each new token appended and fed back in. That's it. Everything else is machinery in service of making that one prediction good.

So “a model that writes” is really a model that scores what's likely next, run in a loop. The skill isn't generating; it's the prediction underneath. Here is that one prediction, for real, from the tiny model this lab builds in Part 1:

A model is a function, not a mind

It helps to picture a giant mathematical function: text in → a probability for every possible next token out. The function's behaviour is fixed by its parameters: numbers set during training. No look-ups of “facts,” no rules someone wrote, just numbers, multiplied and added, shaped by training to make good predictions.

Those numbers are the function's dials, each one adjustable. The umbrella name is parameters; in everyday use they're just as often called the model's weights (strictly, the weights are the multipliers and a smaller set of biases are the offsets — see §4 — but “weights” is the common shorthand for the whole lot). Set every dial the right way and the output goes from gibberish to fluent English; that one good setting is the trained model. So “a 3-million-parameter model” (ours) just means 3 million dials, and a frontier model has hundreds of billions, the largest into the trillions. The dials are turned only once, during training (§7) — frozen afterwards; the single knob you actually touch at generation is temperature (§8).

2

Text becomes numbers (tokens)

A model can't do arithmetic on letters, so the first move is to turn text into numbers. The text is chopped into tokens: common chunks (whole words like fox, or word-pieces), each with an integer ID (its index in a fixed list called the vocabulary). “fox” might be token #1234. That's all a token is to the model: an ID. There's more than one way to chop, and the choice matters enormously:

The reverse runs at the end: the model's predicted ID is mapped back to its chunk of text, and the pieces are glued together into words. Part 1 builds the tokenizer →

The ID itself means nothing

Don't read anything into the numbers: an ID is a coat-check ticket, not a description. #1234 says nothing about foxes, and #1235 is not “one more” than fox; renumber the whole vocabulary, retrain, and you'd get an equally good model. (In practice IDs reflect the order the tokenizer learned its chunks, but the model never uses the number as a number — only as a reference: “fetch row #1234.”) Where meaning enters is what that row holds: the embedding, next.

3

Tokens become vectors (embeddings)

If the ID is just a ticket, where does meaning live? In what the ticket fetches: each token's ID points to a list of numbers, its embedding (256 numbers in our tiny model). Think of those numbers as coordinates that place the token in a vast “meaning space,” where tokens used in similar ways land near each other.

Attributes = dimensions

A token's embedding is a point in 256-dimensional space: 256 numbers, one per dimension. Each dimension is a learned attribute (feature): a mathematical abstraction capturing some statistically-shared pattern across tokens. They don't map cleanly to human concepts, but it's often genuinely helpful to imagine them, loosely, as fuzzy attributes — “animal-ness”, “furriness”, “size” — held lightly. (A token's values on the dimensions are part of the model's parameters; the dimensions themselves are the embedding's axes.)

If you like your philosophy, this should ring a bell: it's Plato's Theory of Forms, rediscovered by gradient descent. Each dimension is an ideal quality, a Form, that no actual word embodies perfectly, and a token's coordinate on it measures how much the word participates in that Form. The model has never seen a fox; from text alone it has assembled a realm of abstractions, of which every particular “fox” on the page is an imperfect shadow.

Where do the embeddings come from?

Not from the letters, and not computed on the fly: they're learned, then looked up. The model keeps an embedding table (one row per vocabulary token). “fox” becomes an integer ID, and that ID simply indexes the table; row #ID is its 256 numbers. There's no arithmetic on f-o-x.

Those numbers start as small random values and are parameters like any other: gradient descent nudges them, step by step, to lower the loss. After training the table is frozen, so the lookup is deterministic (same token → same row), but the row was learned, not derived from the spelling. (Train again with a different random seed and “fox” settles on a different, equally-good vector.) Tokens used in similar contexts get pushed toward similar rows, which is exactly why the clusters above emerge on their own, with no one labelling them.

4

The linear layer (the core operation)

Almost the entire network is one operation, repeated: the linear layer, y = Wx + b. It takes a vector of numbers in and produces a new vector out, where each output is a weighted sum of all the inputs plus an offset. Stack the per-output weight-rows into a grid W and the offsets into a vector b, and that's the whole layer: the school-line y = mx + c, vectorised. The diagram below builds it from one output up to the whole model.

Parameters vs. tokens: the part people mix up

A token doesn't have parameters. The parameters — every W (the weights) and b (the biases) — are the model: fixed after training and shared, so the exact same numbers process every token, at every position. A token is just data flowing through them.

And the weights in the picture are a tiny slice: one output of one layer. Our tiny GPT stacks 4 blocks (each with several Ws) plus the embedding and the head; add them all up and you get the ~3.2M parameters. One layer's W might be 256×1024 (~262k numbers); the whole model is ~3.2M.

And a linear layer transforms one token at a time. The model's real job (read a string of tokens and predict the next) needs tokens to share information, which is attention's job (next section), not the linear layers. 5

The bend (activations)

Stacking linear layers has a catch: by itself, it buys nothing. Double a number, then triple it. Two steps, yet all you've really done is multiply by six, which is one step. Every stack of straight-line operations collapses this way into a single straight-line operation. So no matter how deep the model went, it could still only draw lines. The fix: after each linear step, apply one simple nonlinear function, a bend. That bend is what lets depth model curves and combinations, not just proportions.

Ours is GELU (a smooth version of ReLU). The famous textbook ones are ReLU (keep positives, zero the rest) and the sigmoid (squash any number into 0–1). The whole kit is just this: Wx + b, then a bend, stacked — plus the two ideas below.

One natural misreading is worth heading off: these curves aren't there to squash numbers into a tidy range. The sigmoid happens to (everything lands between 0 and 1), but ReLU and GELU, the ones modern models actually use, are unbounded: a big input sails through nearly unchanged. (Bounded activations in fact fell out of favour: their flat tails make the learning signal of §7 vanish.) Keeping the network's numbers in a sane, comparable range is a different component's job: LayerNorm, a normalisation step you'll meet inside the block in Part 1. The bend has exactly one job: be not-a-straight-line, so stacking layers buys new shapes instead of collapsing into one.

6

Attention: letting tokens talk

Linear layers process each token on its own. But meaning depends on context: “bank” near “river” vs near “money.” Attention is the one step where positions look at each other: each token forms a query and asks “which earlier tokens matter to me?”, then pulls in a blend of their information. It's how the model carries context forward, the part that makes it a language model and not a bag of independent words.

Why it's the heart of it

Everything else (embeddings, linear layers, the bend) works token-by-token. Attention is the only place information moves between tokens. Stack several attention+MLP blocks and the model can build up rich, context-aware meaning before it ever makes a prediction. Part 1 builds attention →

The field agrees about the “heart” part: the 2017 paper that introduced the transformer (the architecture behind every model in this lab, and behind GPT, Claude, and Gemini) announced it in its title: “Attention Is All You Need”. Attention itself wasn't new; the breakthrough was showing that with enough of it, the rest of the old machinery could be thrown away.

7

How it learns: loss, gradients, gradient descent

Where do the millions of parameters come from? Training. Show the model real text with the next token hidden, let it guess, and measure how wrong the guess was with a single number: the loss (low = confident and right; high = wrong). Training is nothing more than making that number smaller, over and over.

The trick is knowing which way to nudge each of the millions of parameters. That's the gradient: for every parameter, the slope of the loss, telling you which direction, and how hard, reduces the error. Nudge every parameter a little down its slope, and the loss drops. Do it a few thousand times and coherent language emerges. This is gradient descent.

8

Generating text, and the one knob: temperature

Once trained, the model generates by running its prediction in a loop: feed the text so far, get a probability for every next token, pick one, append it, repeat. “Inference” and “generation” are the same thing: running the function forward (no learning).

How you pick from the probabilities is the one knob worth feeling: temperature. Low temperature (~0.5) almost always grabs the most likely token: safe, repetitive. High (~1.1) samples more adventurously: varied, riskier, sometimes incoherent. It's the dial between “careful” and “creative,” and it changes nothing in the model — only how its output is sampled. 9

The honest ceiling, and where this goes

That's the whole machine: text → tokens → embeddings → stacks of (attention + Wx+b + a bend) → a final prediction, all tuned by gradient descent. A frontier model is exactly this, scaled up: more dimensions, more layers, vastly more text and compute. Same ideas; different magnitude.

And the honest ceiling: Part 1's tiny GPT produces believable shapes of language, never knowledge or reasoning. That holds even for the tuned version that writes coherent little stories. A laptop's worth of training can't buy more, and that's fine: the tiny build is for seeing every moving part, not for using. Getting something useful is a different move entirely. Part 2 sets the tiny model aside and starts from a big pretrained open model (4 billion parameters, trained at a scale no laptop can touch; that cost was paid by someone else), then specialises it for one narrow job.
